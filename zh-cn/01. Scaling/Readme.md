# 第 1 章：从零扩展到数百万用户

## 引言
要把系统扩展到支撑数百万用户，是一段复杂且需要反复迭代、持续改进和优化的过程。本章介绍如何从单服务器架构开始，逐步扩展架构以应对数百万用户。

---

## 第 1 节：单服务器架构
最初，所有组件（Web 应用、数据库、缓存）都运行在同一台服务器上。

<div style="margin-left:3rem">
   <img src="../../01.%20Scaling/images/single-server.png" width="400" />
</div>

### 请求流程
1. 用户通过域名（例如 `api.mysite.com`）访问应用，DNS 会将域名解析为 IP 地址。
2. Web 服务器的 IP 地址会返回给浏览器或移动应用。
3. 客户端向 Web 服务器发送 HTTP 请求，服务器返回 HTML 或 JSON 响应。

### 流量来源
1. <strong>Web 应用：</strong>使用 Python、Java 等服务端语言处理业务逻辑，并使用 JavaScript、HTML 等客户端语言负责展示。
2. <strong>移动应用：</strong>通过 HTTP 和 JSON 与 Web 服务器通信，以轻量格式交换数据。

---

## 第 2 节：拆分数据库
随着用户规模增长，可以将数据库迁移到专用服务器，使 Web 层和数据库层能够独立扩展。

<div style="margin-left:3rem">
   <img src="../../01.%20Scaling/images/database.png" width="400" />
</div>

### 数据库类型

1. <strong>关系型数据库（SQL）：</strong>以表格形式存储结构化数据，例如 MySQL、PostgreSQL。
2. <strong>非关系型数据库（NoSQL）：</strong>适用于非结构化数据或低延迟场景，类型包括：
   - 键值存储
   - 图数据库
   - 列存储
   - 文档存储

以下情况可以考虑使用非关系型数据库：
   - 应用要求极低的延迟。
   - 数据是非结构化的，或者数据之间没有关系。
   - 只需要序列化和反序列化数据（JSON、XML、YAML 等）。
   - 需要存储海量数据。

## 第 3 节：纵向扩展与横向扩展
### 纵向扩展
- 为现有服务器增加资源，例如 CPU 和 RAM。
- 受硬件上限约束，并且缺少冗余。

### 横向扩展
- 向服务器集群中增加服务器，更适合大规模系统。
- 使用负载均衡器在多台服务器之间路由请求。

---

## 第 4 节：负载均衡器

<div style="margin-left:3rem">
   <img src="../../01.%20Scaling/images/load-balancer.png" width="400" />
</div>

**负载均衡器**会把流量分配到多台服务器上，主要优点包括：
1. 冗余：服务器宕机时，可以将流量切换到其他服务器。
   - 如果服务器 1 宕机，所有流量都会转发到服务器 2。
2. 可扩展性：流量激增时，可以方便地增加服务器。
   - 网站流量快速增长时，可以增加服务器来处理额外流量。

## 第 5 节：数据库复制

<div style="margin-left:3rem">
   <img src="../../01.%20Scaling/images/database-replication.png" width="400" />
</div>

### 主从模型
- <strong>主数据库：</strong>负责处理写操作。
   - 所有修改数据的命令，例如插入、删除或更新，都必须发送到主数据库。
- <strong>从数据库：</strong>负责处理读操作，以提升性能和可靠性。
   - 大多数应用的读写比都较高，因此系统中的从数据库通常多于主数据库。

### 优点
1. 通过并行读取提升性能。
2. 通过冗余提高可用性和数据可靠性。

### 故障处理
- 如果只有一个从数据库且它宕机，读操作会暂时转发到主数据库。
- 如果有多个从数据库，读操作会转发到其他健康的从数据库，并用新服务器替换故障服务器。
- 如果主数据库宕机，会提升一个从数据库作为新的主数据库。
- 在生产系统中，被选中的从数据库可能不是最新的，因此需要运行数据恢复脚本来更新数据。多主复制和循环复制等方式也可能有所帮助。

## 第 6 节：缓存
**缓存**将频繁访问的数据保存在内存中，以降低数据库负载。缓存层是临时的数据存储层，速度远快于数据库。

<div style="margin-left:3rem">
   <img src="../../01.%20Scaling/images/cache.png" width="500" />
</div>

### 缓存设计注意事项
1. <strong>适用场景：</strong>数据读取频繁、修改较少时，可以考虑使用缓存。
2. <strong>过期策略：</strong>缓存数据过期后会被移除。如果没有设置过期策略，缓存数据会一直保存在内存中。
3. <strong>一致性：</strong>需要让数据存储和缓存保持同步。由于修改数据存储和缓存的操作不在同一个事务中，可能出现不一致。
4. <strong>降低故障风险：</strong>单台缓存服务器可能成为单点故障。建议在多个数据中心部署多台缓存服务器，避免 SPOF。
5. <strong>淘汰策略：</strong>缓存空间用满后，需要淘汰部分数据以释放内存。LRU 是最常见的缓存淘汰策略。

---

## 第 7 节：内容分发网络（CDN）
**CDN**通过在地理位置分散的服务器上缓存静态内容（图片、CSS、JavaScript）来缩短加载时间。

<div style="margin-left:3rem">
   <img src="../../01.%20Scaling/images/cdn.png" width="400" />
</div>

### 工作流程
1. 用户从距离最近的 CDN 服务器请求内容。
2. 如果 CDN 上没有缓存该内容，就从源站获取并缓存。

### CDN 注意事项
1. <strong>成本：</strong>CDN 由第三方提供，通常会对进出 CDN 的数据传输收费。
2. <strong>缓存过期：</strong>缓存过期时间不宜过长或过短。
3. <strong>CDN 故障回源：</strong>CDN 暂时不可用时，客户端应能检测到问题并从源站请求资源。
4. <strong>文件失效：</strong>文件更新后，应使旧缓存失效，让请求指向更新后的文件。

## 第 8 节：无状态 Web 层
将会话数据移到共享数据存储后，Web 服务器就可以变为无状态。这样可以：
1. 更容易地进行横向扩展。
2. 根据流量自动扩缩容。

</div>

## 第 9 节：多数据中心架构
在多个数据中心部署服务可以提高可用性并降低延迟，常用策略包括：

<div style="margin-left:3rem">
   <img src="../../01.%20Scaling/images/data-center.png" width="400" />
</div>

1. <strong>GeoDNS 路由：</strong>将用户请求导向最近的数据中心。
2. <strong>数据复制：</strong>在多个数据中心之间同步数据，避免数据不一致。

### 关键注意事项
- <strong>流量重定向：</strong>需要有效的工具将流量导向正确的数据中心。
- <strong>数据同步：</strong>常见做法是在多个数据中心之间复制数据。
- <strong>测试与部署：</strong>自动化部署工具对于保持各数据中心的服务一致至关重要。

---

## 第 10 节：消息队列
**消息队列**是一种持久化组件，数据存储在内存中，支持异步通信。它可以作为缓冲区，并分发异步请求。

<div style="margin-left:3rem">
   <img src="../../01.%20Scaling/images/message-queue.png" width="500" />
</div>

- 输入服务（称为生产者或发布者）创建消息，并将其发布到消息队列。
- 其他服务（称为消费者或订阅者）连接到队列，并执行消息中定义的操作。

## 第 12 节：数据库扩展
### 纵向扩展
- 增加硬件资源，但受物理条件和成本限制。
- 存在多项缺点：
   - 单点故障的风险更高。
   - 纵向扩展的总体成本较高。

### 横向扩展（分片）

<div style="margin-left:3rem">
   <img src="../../01.%20Scaling/images/horizontal-scaling.png" width="400" />
</div>

- 使用键（例如 `user_id`）将数据拆分到多个分片中。
   - 分片是将大型数据库拆分为更小、易于管理的部分，每个部分称为一个分片。
   - 所有分片使用相同的 schema，但各分片实际存储的数据不同。
- 分片键对分片策略至关重要。选择分片键时，应确保数据可以均匀分布。

#### 挑战
1. <strong>重新分片：</strong>以下情况需要重新分片：
   - 数据快速增长，单个分片无法再容纳更多数据。
   - 数据分布不均，导致部分分片比其他分片更早耗尽容量。
   - 可以使用一致性哈希来应对这些问题。

2. <strong>名人问题：</strong>对某个分片的访问过于集中，可能导致服务器过载。
   - 一种解决办法是为每位名人分配一个独立分片。

3. <strong>关联查询与反规范化：</strong>数据库被拆分到多台服务器后，很难跨分片执行关联查询。
   - 常见的变通办法是对数据库进行反规范化，让查询可以在单张表中完成。

---

## 结论
### 要点
1. 保持 Web 层无状态。
2. 在每一层构建冗余。
3. 使用缓存和 CDN 优化性能。
4. 通过分片扩展数据层。
5. 解耦组件以提高灵活性。

本章为构建可扩展系统打下基础，使系统能够支撑数百万用户。
