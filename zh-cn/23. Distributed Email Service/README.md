# 第 23 章：分布式邮件服务

## 简介

本章将设计一个类似 **Gmail** 的**分布式邮件服务**。

2020 年，Gmail 有 18 亿活跃用户，Outlook 在全球有 4 亿用户。

---

## 第一步：理解问题并明确设计范围

- C：有多少用户使用这个系统？
- I：10 亿用户。
- C：我认为以下功能比较重要：身份验证、发送和接收邮件、获取邮件、筛选邮件、搜索邮件和反垃圾邮件保护。
- I：这些功能都不错，暂时不用考虑身份验证。
- C：用户如何连接邮件服务器？
- I：通常邮件客户端通过 SMTP、POP、IMAP 连接，但本题中我们使用 HTTP。
- C：邮件可以有附件吗？
- I：可以。

### **非功能性需求**

- **可靠性**：不能丢失数据。
- **可用性**：使用复制避免单点故障，并容忍系统部分故障。
- **可扩展性**：用户规模增长时，系统应能继续承载负载。
- **灵活性和可扩展能力**：系统应便于灵活扩展新功能。这也是我们选择 HTTP 而不是 SMTP 等邮件协议的原因之一。

### **粗略估算**

- **10 亿用户**。
- 假设每人每天发送 10 封邮件，则每秒约发送 **10 万封邮件**。
- 假设每人每天接收 40 封邮件，每封邮件平均有 50 KB 元数据，则每年需要 **730 PB 存储空间**。
- 假设 20% 的邮件带有附件，平均附件大小为 500 KB，则每年需要 **1460 PB 存储空间**。

## 第二步：提出高层设计并取得认可

### **邮件基础知识**

发送和接收邮件会用到多种协议：

- **SMTP**：服务器之间发送邮件的标准协议。
- **POP**：从远程邮件服务器接收并下载邮件到本地客户端的标准协议。邮件取回后会从远程服务器删除。
- **IMAP**：类似 POP，用于从远程服务器接收和下载邮件，但会在服务器端保留邮件。
- **HTTPS**：严格来说不是邮件协议，但可以用于基于 Web 的邮件客户端。

除了邮件协议之外，邮件服务器还需要配置 DNS 记录，即 MX 记录：

    <img src="../../23.%20Distributed%20Email%20Service/images/dns-lookup.png" alt="DNS 查询" width="500" />
</div>

邮件附件会以 Base64 编码发送。大多数邮件服务通常限制附件大小为 25 MB。具体限制可以配置，并且个人账户和企业账户可能不同。

### **传统邮件服务器**

用户数量有限并且所有用户连接到同一台服务器时，传统邮件服务器运行良好。

<div style="margin-left:3rem">
    <img src="../../23.%20Distributed%20Email%20Service/images/traditional-mail-server.png" alt="传统邮件服务器" width="500" />
</div>

- Alice 登录 Outlook 邮箱并点击“发送”。邮件通过 SMTP 发送到 Outlook 邮件服务器。
- Outlook 服务器查询 DNS，找到 gmail.com 的 MX 记录，然后将邮件传给 Gmail 服务器。这一步也使用 SMTP。
- Bob 通过 IMAP 或 POP 从 Gmail 服务器获取邮件。

传统邮件服务器会将邮件存储在本地文件系统中，每封邮件单独保存为一个文件。

<div style="margin-left:3rem">
    <img src="../../23.%20Distributed%20Email%20Service/images/local-dir-storage.png" alt="本地目录存储" width="500" />
</div>

随着规模扩大，磁盘 I/O 会成为瓶颈。此外，这种方式也无法满足高可用性和可靠性要求，因为磁盘可能损坏，服务器也可能宕机。

### **分布式邮件服务器**

分布式邮件服务器面向现代使用场景，解决了现代系统的可扩展性问题。

这类服务器仍然可以支持原生邮件客户端使用 IMAP/POP，并通过 SMTP 在服务器之间交换邮件。

对于功能丰富的 Web 邮件客户端，通常使用基于 HTTP 的 RESTful API。

API 示例：

- `POST /v1/messages`：向 To、Cc、Bcc 中的收件人发送邮件。
- `GET /v1/folders`：返回邮箱账户中的所有文件夹。

响应示例：

~~~text
[{id: string        文件夹唯一标识符。
  name: string      文件夹名称。
                    根据 RFC6154 [9]，默认文件夹可以是：
                    All、Archive、Drafts、Flagged、Junk、Sent 和 Trash。
  user_id: string   所属账户的引用
}]
~~~

- `GET /v1/folders/{:folder_id}/messages`：分页返回文件夹中的所有邮件。
- `GET /v1/messages/{:message_id}`：获取指定邮件的全部信息。

响应示例：

~~~json
{
  user_id: string                      // 所属账户的引用
  from: {name: string, email: string}  // 发件人的姓名和邮箱
  to: [{name: string, email: string}]  // 收件人列表，每项包含姓名和邮箱
  subject: string                      // 邮件主题
  body: string                         // 邮件正文
  is_read: boolean                     // 邮件是否已读
}
~~~

分布式邮件服务器的高层设计如下：

<div style="margin-left:3rem">
    <img src="../../23.%20Distributed%20Email%20Service/images/high-level-architecture.png" alt="高层架构" width="500" />

- **Web 邮箱**：用户通过浏览器发送和接收邮件。
- **Web 服务器**：面向公网的请求/响应服务，用于管理登录、注册、用户资料等。
- **实时服务器**：向客户端实时推送新邮件。使用 WebSocket 实现实时通信；对于不支持 WebSocket 的旧浏览器，则回退到长轮询。
- **元数据数据库**：保存主题、正文、发件人、收件人等邮件元数据。
- **附件存储**：对象存储（例如 Amazon S3），适合存放大文件。
- **分布式缓存**：可以使用 Redis 缓存近期邮件，改善用户体验。
- **搜索存储**：分布式文档存储，用于支持全文搜索。

邮件发送流程如下：

<div style="margin-left:3rem">
    <img src="../../23.%20Distributed%20Email%20Service/images/email-sending-flow.png" alt="邮件发送流程" width="500" />
</div>

- 用户写好邮件并点击“发送”，邮件请求发送到负载均衡器。
- 负载均衡器对过量邮件发送进行限流，并将请求路由到某台 Web 服务器。
- Web 服务器进行基本邮件校验（例如邮件大小），先执行垃圾邮件检查；如果发件人和收件人属于同一个域名，则可以跳过外发流程。
- 基本校验通过后，邮件被放入消息队列（附件通过对象存储引用）。
- 基本校验失败时，邮件进入错误队列。
- SMTP 外发工作进程从外发队列取出邮件，检查垃圾邮件和病毒，并将邮件路由至目标邮件服务器。
- 邮件被存入“已发送邮件”文件夹。

还需要监控外发消息队列的大小。队列过长可能意味着：

- 收件方邮件服务器不可用。可以稍后重试发送，并采用指数退避。
- 消费者数量不足以处理当前负载，可能需要扩容消费者。

邮件接收流程如下：

<div style="margin-left:3rem">
    <img src="../../23.%20Distributed%20Email%20Service/images/email-receiving-flkow.png" alt="邮件接收流程" width="500" />
</div>

- 收到的邮件先到达 SMTP 负载均衡器，再分配给 SMTP 服务器执行邮件接收策略（例如直接丢弃无效邮箱地址）。
- 如果邮件附件很大，可以将附件存入对象存储（例如 S3）。
- 邮件处理工作进程完成初步检查后，将邮件转交给存储、缓存、对象存储和实时服务器。
- 离线用户重新上线后，可以通过 HTTP API 获取新邮件。

## 第三步：深入设计

下面深入讨论其中一些组件。

### **元数据数据库**

邮件元数据有以下特点：

- 邮件头通常较小，且访问频繁。
- 正文大小不一，但通常只读取一次。
- 大多数邮件操作只涉及单个用户，例如获取邮件、标记为已读、搜索邮件。
- 数据的新旧程度会影响访问频率。用户通常只阅读近期邮件。
- 数据可靠性要求高，不能丢失数据。

在 Gmail 或 Outlook 这样的规模下，数据库通常是定制的，以减少每秒输入/输出操作次数（IOPS）。

先看看可选的数据库：

- **关系型数据库**：可以为邮件头和正文建立索引，但这类数据库通常针对较小的数据块进行了优化。
- **分布式对象存储**：适合作为备份存储，但无法高效支持搜索、标记已读等操作。
- **NoSQL**：Gmail 使用 Google BigTable，但它没有开源。

综合来看，现有解决方案似乎都不能完全满足需求。在面试中不可能完整设计一种新的分布式数据库，但应提及它需要具备的特性：

- 单列数据可以达到数 MB。
- 强一致性。
- 设计上尽量减少磁盘 I/O。
- 高可用并具备容错能力。
- 易于创建增量备份。

为了对数据分区，可以使用 `user_id` 作为分区键，使每个用户的数据存放在同一个分片上。这样无法与多个用户共享同一封邮件，但这不属于本题需求。

定义数据表时需要考虑：

- 主键由分区键（用于数据分布）和聚簇键（用于数据排序）组成。
- 需要支持的查询包括：获取用户的所有文件夹、显示文件夹中的所有邮件、创建/获取/删除邮件、获取已读/未读邮件，以及获取会话线程（加分项）。

最后，由于本题强制要求一致性，我们选择让分布式数据库优先保证一致性，而牺牲部分可用性。

因此，发生故障转移或网络分区时，受影响用户的同步/更新操作会短暂不可用。

### **邮件送达能力**

搭建一台可以发送邮件的服务器并不难，但要让邮件进入收件箱很困难，因为邮件服务商会使用垃圾邮件检测算法。

如果只是搭建新的邮件服务器并开始发送邮件，邮件很可能会进入垃圾邮件文件夹。

可以采取以下措施：

- **专用 IP**：使用专用 IP 发送邮件，否则收件方服务器可能不信任发件方。
- **邮件分类**：营销邮件应与其他邮件分开，避免重要邮件被判为垃圾邮件。
- **逐步预热 IP 地址**：慢慢建立大型邮件服务商对 IP 的信誉。预热新 IP 需要 2 至 6 周。
- **尽快封禁垃圾邮件发送者**：避免发件方信誉受损。
- **反馈处理**：与 ISP 建立反馈循环，跟踪投诉率并尽快封禁垃圾邮件账户。
- **邮件身份验证**：采用常见的反钓鱼机制，例如 SPF（发件人策略框架）、DKIM（域名密钥识别邮件）等。

不必记住所有细节，只要知道构建可靠邮件服务器需要大量领域知识即可。

### **搜索**

搜索可以是根据邮件内容进行全文搜索，也可以是根据发件人、收件人、主题、是否已读等条件进行高级查询。

邮件搜索有一个特点：搜索范围是单个用户的邮箱。由于每次操作都可能需要重新索引，写入量大于读取量；但用户很少使用搜索页面。

比较一下 Google 搜索和邮件搜索：

| 类型 | 搜索范围 | 排序方式 | 准确性 |
|------|----------|----------|--------|
| Google 搜索 | 整个互联网 | 按相关性排序 | 建立索引需要时间，因此结果不是即时的。 |
| 邮件搜索 | 用户自己的邮箱 | 按时间、日期等属性排序 | 索引应快速完成，搜索结果应准确。 |

一种实现方式是使用 Elasticsearch 集群，并使用 `user_id` 作为分区键，将同一用户的数据放到同一个节点：

<div style="margin-left:3rem">
    <img src="../../23.%20Distributed%20Email%20Service/images/elasticsearch.png" alt="Elasticsearch" width="500" />
</div>

变更操作通过 Kafka 异步执行，使服务与重新索引流程解耦。实际搜索则同步完成。

Elasticsearch 是常见的搜索引擎数据库，非常适合为邮件提供全文搜索。

另一种方案是开发自定义搜索系统，以满足特定需求。此处不讨论自定义系统的设计。构建这类系统的核心挑战之一，是让它适应写入密集型工作负载。

可以使用日志结构合并树（LSM Tree）组织磁盘上的索引数据，从而优化写入路径，使其只需顺序写入。Cassandra、BigTable 和 RocksDB 都使用了这项技术。

核心思路是先将数据保存在内存中，达到预设阈值后再合并到下一层（磁盘）：

<div style="margin-left:3rem">
    <img src="../../23.%20Distributed%20Email%20Service/images/lsm-tree.png" alt="LSM Tree" width="500" />
</div>

两种方案的主要权衡如下：

- Elasticsearch 具备一定的扩展能力；自定义搜索引擎则可以针对邮件场景调优，进一步扩展。
- Elasticsearch 是需要与元数据存储并行维护的独立服务；自定义方案可以直接作为数据存储本身。
- Elasticsearch 是现成方案；开发自定义搜索引擎则需要投入大量工程工作。

## 第四步：总结

还可以讨论以下内容：

- **容错能力**：系统的许多部分都可能发生故障，值得讨论如何处理节点故障。
- **合规性**：根据欧洲 GDPR 法律，妥善存储个人身份信息（PII）。
- **安全性**：邮件加密、钓鱼防护、安全浏览等。
- **优化**：例如避免多个用户重复存储相同的附件。
