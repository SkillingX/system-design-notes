# 第 27 章：数字钱包

## 简介

**支付平台**通常包含**钱包服务**，让客户可以在应用内存入资金，以后再提取。

客户也可以使用钱包购买商品和服务，或向其他钱包用户转账。与通过传统支付渠道转账相比，这种方式可能更快、成本更低。

## 第一步：理解问题并明确设计范围

- C：我们是否只关注数字钱包之间的转账？还需要支持其他操作吗？
- I：目前先聚焦于数字钱包之间的转账。
- C：系统每秒需要支持多少笔交易？
- I：假设需要支持 100 万 TPS。
- C：数字钱包对正确性要求很严格。能否假设事务保证足够？
- I：可以。
- C：需要证明系统正确吗？
- I：可以通过对账来发现差异，但对账只能发现差异，不能说明差异的根本原因。我们希望能够从头重放数据，重建整个历史。
- C：能否假设可用性要求为 99.99%？
- I：可以。
- C：需要考虑外汇兑换吗？
- I：不需要，这不在范围内。

总结一下需要支持的内容：

- 支持两个账户之间转移余额。
- 支持 100 万 TPS。
- 可靠性为 99.99%。
- 支持事务。
- 支持重现历史状态。

### **粗略估算**

在云上配置的传统关系型数据库大约可以支持 1000 TPS。

要达到 100 万 TPS，需要 1000 个数据库节点。但每笔转账包含两个资金变动，因此实际需要支持 200 万 TPS。

一个设计目标是提高单个节点可处理的 TPS，从而减少数据库节点数量。

| 每节点 TPS | 节点数 |
|------------|--------|
| 100 | 20,000 |
| 1,000 | 2,000 |
| 10,000 | 200 |

## 第二步：提出高层设计并取得认可

### **API 设计**

本次面试只需要支持一个端点：

~~~http
POST /v1/wallet/balance_transfer - 在两个钱包之间转移余额
~~~

请求参数：from_account、to_account、amount（使用字符串以避免精度损失）、currency 和 transaction_id（幂等键）。

示例响应：

~~~json
{
    "status": "success",
    "transaction_id": "01589980-2664-11ec-9621-0242ac130002"
}
~~~

### **内存分片方案**

钱包应用会维护每个用户账户的余额。

一种合适的数据结构是 `map<user_id, balance>`，可以通过 Redis 这样的内存存储实现。

单个 Redis 节点无法承受 100 万 TPS，因此需要将 Redis 集群分区到多个节点。

分区算法示例：

~~~java
String accountID = "A";
Int partitionNumber = 7;
Int myPartition = accountID.hashCode() % partitionNumber;
~~~

可以使用 Zookeeper 保存分区数量和 Redis 节点地址，因为它是高可用的配置存储。

最后，钱包服务是一个负责执行转账操作的无状态服务，可以轻松进行水平扩展：

</div>

虽然这个方案解决了可扩展性问题，但无法让余额转账以原子方式执行。

### **分布式事务**

一种处理事务的方式是在标准的分片关系型数据库之上使用两阶段提交协议：

<div style="margin-left:3rem">
    <img src="../../27.%20%20Digital%20Wallet/images/distributed-transactions-relational-dbs.png" alt="关系型数据库中的分布式事务" width="500" />
</div>

两阶段提交（2PC）协议的工作方式如下：

<div style="margin-left:3rem">
    <img src="../../27.%20%20Digital%20Wallet/images/2pc-protocol.png" alt="两阶段提交协议" width="500" />
</div>

- 协调器（钱包服务）像平常一样在多个数据库中执行读写操作。
- 应用准备好提交事务时，协调器要求所有数据库准备提交。
- 如果所有数据库都回复“是”，协调器就要求数据库提交事务。
- 否则，协调器要求所有数据库中止事务。

2PC 方案的缺点：

- 锁竞争会导致性能不佳。
- 协调器是单点故障。

### **使用 Try-Confirm/Cancel（TC/C）的分布式事务**

TC/C 是 2PC 的一种变体，使用补偿事务：

- 协调器要求所有数据库为事务预留资源。
- 协调器收集数据库的回复：如果全部成功，就要求数据库尝试确认；如果失败，就要求数据库尝试取消。

TC/C 与 2PC 的一个重要区别是：2PC 执行一个事务，而 TC/C 执行两个独立事务。

TC/C 分为以下阶段：

| 阶段 | 操作 | A | C |
|------|------|---|---|
| 1 | Try（尝试） | 余额变动：-$1 | 不操作 |
| 2 | Confirm（确认） | 不操作 | 余额变动：+$1 |
|  | Cancel（取消） | 余额变动：+$1 | 不操作 |

第一阶段：尝试。

<div style="margin-left:3rem">
    <img src="../../27.%20%20Digital%20Wallet/images/try-phase.png" alt="尝试阶段" width="500" />
</div>

- 协调器在 A 的数据库中启动本地事务，将 A 的余额减少 1 美元。
- C 的数据库收到一条 NOP（不执行任何操作）指令。

第二阶段 A：确认。

<div style="margin-left:3rem">
    <img src="../../27.%20%20Digital%20Wallet/images/confirm-phase.png" alt="确认阶段" width="500" />
</div>

- 如果两个数据库都回复“是”，则进入确认阶段。
- A 的数据库收到 NOP；C 的数据库则被指示通过本地事务将 C 的余额增加 1 美元。

第二阶段 B：取消。

<div style="margin-left:3rem">
    <img src="../../27.%20%20Digital%20Wallet/images/cancel-phase.png" alt="取消阶段" width="500" />
</div>

- 如果第一阶段的任何操作失败，则进入取消阶段。
- A 的数据库收到指令，将 A 的余额增加 1 美元；C 的数据库收到 NOP。

下面比较 2PC 和 TC/C：

| 协议 | 第一阶段 | 第二阶段：成功 | 第二阶段：失败 |
|------|----------|----------------|----------------|
| 2PC | 尚未执行事务 | 提交或取消所有事务 | 取消所有事务 |
| TC/C | 所有事务均已完成（提交或取消） | 根据需要执行新事务 | 撤销已经提交的事务 |

TC/C 也称为补偿式分布式事务。其高层操作由业务逻辑处理。

TC/C 的其他特性：

- 与数据库无关，只要数据库支持事务即可使用。
- 分布式事务的细节和复杂性需要由业务逻辑处理。

### **TC/C 的故障模式**

如果协调器在流程中途崩溃，就需要恢复中间状态。可以在数据库分片中维护阶段状态表，并以原子方式更新：

<div style="margin-left:3rem">
    <img src="../../27.%20%20Digital%20Wallet/images/phase-status-tables.png" alt="阶段状态表" width="500" />
</div>

状态表中包含：

- 分布式事务的 ID 和内容。
- Try 阶段的状态：未发送、已发送、已收到响应。
- 第二阶段的名称：Confirm 或 Cancel。
- 第二阶段的状态。
- 乱序标记（后文解释）。

使用 TC/C 时需要注意：分布式事务执行期间，账户状态可能会短暂地彼此不一致：

<div style="margin-left:3rem">
    <img src="../../27.%20%20Digital%20Wallet/images/unbalanced-state.png" alt="暂时不平衡的状态" width="500" />
</div>

只要系统能够始终从该状态恢复，并且用户无法利用中间状态花掉尚未到账的资金，这种情况就可以接受。通过始终先执行扣款、再执行入账，可以满足这一点。

| Try 阶段选项 | 账户 A | 账户 C |
|--------------|--------|--------|
| 选项 1 | -$1 | NOP |
| 选项 2（无效） | NOP | +$1 |
| 选项 3（无效） | -$1 | +$1 |

上表中的选项 3 无效，因为如果不使用 2PC，就无法保证跨不同数据库原子执行事务。

还需要处理一种边缘情况：乱序执行。

<div style="margin-left:3rem">
    <img src="../../27.%20%20Digital%20Wallet/images/out-of-order-execution.png" alt="乱序执行" width="500" />
</div>

数据库可能先收到 Cancel 操作，然后才收到 Try 操作。可以在阶段状态表中加入乱序标记来处理：收到 Try 操作时，先检查乱序标记；如果标记已设置，就返回失败。

### **使用 Saga 的分布式事务**

另一种常见方案是 Saga，它是一种在微服务架构中实现分布式事务的标准模式。

它的工作方式如下：

- 所有操作按顺序排列。每个操作都在各自的数据库中独立执行。
- 操作从头到尾依次执行。
- 某个操作失败时，整个流程通过补偿操作从当前位置回滚到起点。

<div style="margin-left:3rem">
    <img src="../../27.%20%20Digital%20Wallet/images/saga.png" alt="Saga" width="500" />
</div>

如何协调工作流？可以采用两种方式：

- **编舞（Choreography）**：Saga 中的所有服务都订阅相关事件，并执行自己负责的部分。
- **编排（Orchestration）**：由一个协调器按正确顺序指示所有服务执行各自的任务。

编舞方式的挑战在于，业务逻辑分散在多个异步通信的服务中。编排方式更容易管理复杂性，因此在数字钱包系统中通常更受青睐。

下面比较 TC/C 和 Saga：

| 比较项 | TC/C | Saga |
|--------|------|------|
| 补偿操作 | 在 Cancel 阶段 | 在回滚阶段 |
| 中央协调 | 是 | 是（编排模式） |
| 操作执行顺序 | 任意 | 线性 |
| 是否可并行执行 | 可以 | 不可以（线性执行） |
| 是否可能看到部分不一致状态 | 是 | 是 |
| 由应用还是数据库处理逻辑 | 应用 | 应用 |

主要区别是 TC/C 可以并行执行，因此方案选择取决于延迟要求：如果需要低延迟，应采用 TC/C。

无论选择哪种方案，仍然需要支持审计和历史重放，以便从故障状态中恢复。

### **事件溯源**

现实中的数字钱包应用可能需要接受审计，并回答以下问题：

- 我们能否知道账户在任意时间点的余额？
- 如何确认历史余额和当前余额都是正确的？
- 代码变更后，如何证明系统逻辑仍然正确？

事件溯源可以帮助回答这些问题。

事件溯源包含四个概念：

- **命令（Command）**：现实世界中希望执行的操作，例如从账户 A 向账户 B 转账 1 美元。命令需要全局排序，因此会放入 FIFO 队列。
  - 命令不同于事件，可能失败，也可能因 I/O 或无效状态等原因具有随机性。
  - 命令可以生成零个或多个事件。
  - 事件生成可能包含随机性，例如外部 I/O；后文会再讨论这一点。
- **事件（Event）**：系统中已经发生的历史事实，例如“已从 A 向 B 转账 1 美元”。
  - 与命令不同，事件是系统中已经发生的事实。
  - 和命令一样，事件也需要排序，因此会放入 FIFO 队列。
- **状态（State）**：事件导致的变化。例如，一个记录账户和余额的键值存储。
- **状态机（State machine）**：驱动事件溯源流程，主要负责验证命令并应用事件来更新系统状态。
  - 状态机应当是确定性的，因此不应读取外部 I/O 或依赖随机性。

<div style="margin-left:3rem">
    <img src="../../27.%20%20Digital%20Wallet/images/event-sourcing.png" alt="事件溯源" width="500" />
</div>

下面从动态角度看事件溯源：

<div style="margin-left:3rem">
    <img src="../../27.%20%20Digital%20Wallet/images/dynamic-event-sourcing.png" alt="事件溯源动态流程" width="500" />
</div>

在钱包服务中，命令就是余额转账请求。可以将它们放入 FIFO 队列，例如 Kafka：

<div style="margin-left:3rem">
    <img src="../../27.%20%20Digital%20Wallet/images/command-queue.png" alt="命令队列" width="500" />
</div>

完整流程如下：

<div style="margin-left:3rem">
    <img src="../../27.%20%20Digital%20Wallet/images/wallet-service-state-macghine.png" alt="钱包服务状态机" width="500" />
</div>

- 状态机从命令队列读取命令。
- 从数据库读取余额状态。
- 验证命令。如果命令有效，则为两个账户各生成一个事件。
- 读取下一个事件，并通过更新数据库中的余额（状态）来应用事件。

事件溯源的主要优点是可重现性。在这种设计中，所有状态更新操作都会以不可变历史的形式保存，记录每一次余额变化。

可以随时从头重放事件，重建历史余额。由于事件列表不可变且状态机具有确定性，因此可以确保成功重放并恢复到任何中间状态。

<div style="margin-left:3rem">
    <img src="../../27.%20%20Digital%20Wallet/images/historical-states.png" alt="历史状态" width="500" />
</div>

本节开始提出的审计问题都可以通过事件溯源解决：

- 我们能否知道账户在任意时间点的余额？可以从头重放事件，直到目标时间点。
- 如何确认历史余额和当前余额正确？可以从头重新计算所有事件并校验正确性。
- 代码变更后如何证明系统逻辑正确？可以让不同版本的代码处理同一组事件，并确认结果一致。

可以使用 CQRS 架构回答客户端关于余额的查询：由多个只读状态机构成的查询端，根据不可变事件列表查询历史状态：

## 第三步：深入设计

本节讨论一些性能优化，因为系统仍需扩展到 100 万 TPS。

### **高性能事件溯源**

首先，将命令和事件保存在本地磁盘，而不是 Kafka 这样的外部存储。

这样可以避免网络延迟。此外，由于操作只有追加写入，通常也适合 HDD。

接下来，将近期命令和事件缓存在内存中，减少从磁盘重新加载数据的时间。

在底层，可以利用 mmap 命令实现这些优化。它将数据存储在本地磁盘，同时将数据缓存到内存中：

<div style="margin-left:3rem">
    <img src="../../27.%20%20Digital%20Wallet/images/mmap-optimization.png" alt="mmap 优化" width="500" />
</div>

还可以使用 SQLite 这样的文件系统本地数据库存储状态。RocksDB 也是不错的选择。

本设计选择 RocksDB，因为它使用针对写入操作优化的日志结构合并树（LSM）。读取性能则通过缓存优化。

<div style="margin-left:3rem">
    <img src="../../27.%20%20Digital%20Wallet/images/rocks-db-approach.png" alt="RocksDB 方案" width="500" />
</div>

为了优化状态重现，可以定期将快照保存到磁盘。这样就不必每次都从头重建目标状态。快照可以作为大型二进制文件存储在分布式文件存储中，例如 HDFS：

<div style="margin-left:3rem">

### **可靠的高性能事件溯源**

前面讨论的优化很有效，但会使服务变为有状态服务。为了保证可靠性，需要引入某种复制机制。

在此之前，先分析系统中哪些数据需要高可靠性：

- 状态和快照都可以通过重放事件列表重新生成，因此只需确保事件列表可靠。
- 可能有人认为可以通过命令列表随时重建事件列表，但这并不成立，因为命令具有非确定性。
- 因此，只需要为事件列表提供高可靠性。

为了保证事件可靠，需要在多个节点之间复制事件列表，并确保：

- 不会丢失数据。
- 同一日志文件中的数据在所有副本上保持相同的相对顺序。

可以使用 Raft 等共识算法实现这些保证。

Raft 中有一个活跃的领导者和多个被动跟随者。领导者故障时，某个跟随者会接替它。只要超过半数节点正常运行，系统就可以继续工作。

<div style="margin-left:3rem">
    <img src="../../27.%20%20Digital%20Wallet/images/raft-replication.png" alt="Raft 复制" width="500" />
</div>

使用这种方案时，所有节点都会根据事件列表更新状态。Raft 确保领导者和跟随者拥有相同的事件列表。

### **分布式事件溯源**

目前我们已经设计出一种单节点性能高且可靠的系统。

还需要解决一些限制：

- 单个 Raft 组的容量有限。达到一定规模后，需要对数据分片并实现分布式事务。
- 在 CQRS 架构中，请求/响应流程较慢。客户端需要定期轮询系统，才能知道钱包何时更新。

轮询无法实现实时通知，因此用户可能需要等待一段时间才能得知余额更新。此外，如果轮询频率过高，也会让查询服务过载：

<div style="margin-left:3rem">
    <img src="../../27.%20%20Digital%20Wallet/images/polling-approach.png" alt="轮询方案" width="500" />
</div>

为了减轻系统负载，可以引入反向代理，由它代替用户发送命令并轮询结果：

<div style="margin-left:3rem">
    <img src="../../27.%20%20Digital%20Wallet/images/reverse-proxy.png" alt="反向代理" width="500" />
</div>

这样可以通过一次请求获取多个用户的数据，减轻系统负载，但仍然不能满足实时接收结果的要求。

最后一种改进是让只读状态机在结果可用时主动推送给反向代理。这样用户会感觉余额实时更新：

<div style="margin-left:3rem">
    <img src="../../27.%20%20Digital%20Wallet/images/push-state-machines.png" alt="状态机推送" width="500" />
</div>

最后，为了进一步扩展系统，可以将系统拆分到多个 Raft 组，并使用编排器在其上实现分布式事务，可以采用 TC/C 或 Saga：

<div style="margin-left:3rem">
    <img src="../../27.%20%20Digital%20Wallet/images/sharded-raft-groups.png" alt="分片后的 Raft 组" width="500" />
</div>

下面展示最终系统中一笔余额转账请求的完整生命周期：

- 用户 A 向 Saga 协调器发送分布式事务，其中包含两个操作：`A-1` 和 `C+1`。
- Saga 协调器在阶段状态表中创建记录，以跟踪事务状态。
- 协调器确定需要向哪些分区发送命令。
- 分区 1 的 Raft 领导者收到 `A-1` 命令，进行验证，将其转换为事件，并将事件复制到 Raft 组内的其他节点。
- 事件结果同步到读取状态机，后者将响应推送回协调器。
- 协调器创建一条表示操作成功的记录，然后继续执行下一个操作：`C+1`。
- 下一个操作与第一个操作类似：确定分区、发送命令、执行操作，并由读取状态机推送响应。
- 协调器创建一条表示第二个操作也成功的记录，最后将结果通知客户端。

---

## 第四步：总结

设计演进过程如下：

- 从基于内存 Redis 的方案开始。它的问题是存储不具备持久性。
- 随后改用关系型数据库，并在其上通过 2PC、TC/C 或分布式 Saga 执行分布式事务。
- 然后引入事件溯源，使所有操作都可以审计。
- 起初使用外部数据库和队列存储数据，但这种方式性能不佳。
- 接着改为本地文件存储，利用只追加操作的性能，并通过缓存优化读取路径。
- 上一步方案虽然性能较好，但缺乏持久性，因此加入 Raft 共识和复制，避免单点故障。
- 还采用 CQRS 和反向代理，代表用户管理事务生命周期。
- 最后，将数据拆分到多个 Raft 组，并通过 TC/C 或分布式 Saga 协调跨组事务。
