# 第 10 章：设计通知系统

## 引言
**通知系统**是现代应用的重要组成部分，可以及时发送产品通知、活动消息、优惠和提醒。通知渠道包括：
1. **推送通知**（移动端或桌面端）
2. **短信**
3. **电子邮件**

本章重点讨论如何设计一个每天能够发送数百万条通知的可扩展系统。

---

## 第 1 步：理解问题
### 需求
- **通知类型：**推送通知、短信和电子邮件。
- **投递要求：**软实时系统，尽量减少延迟。
- **平台：**iOS、Android 和桌面端。
- **触发方式：**通知可以由客户端应用触发，也可以由服务器定时触发。
- **规模：**
  - **推送通知：**每天 1,000 万条。
  - **短信：**每天 100 万条。
  - **电子邮件：**每天 500 万封。
- **退订支持：**用户可以关闭特定类型的通知。

---

## 第 2 步：高层设计

### 组件

1. **通知渠道：**
   - **iOS 推送通知：**使用 **Apple Push Notification Service（APNS）**。
   - **Android 推送通知：**使用 **Firebase Cloud Messaging（FCM）**。
   - **短信：**使用 Twilio 或 Nexmo 等第三方服务。
   - **电子邮件：**使用 SendGrid 或 Mailchimp 等商业邮件服务。

2. **收集联系信息：**
   <div style="margin-left:3rem">
      <img src="../../10.%20Notification%20System/images/contact-info-gathering.png" alt="Contact Info Gathering" width="500">
   </div>

   - 在安装应用或注册时收集设备令牌、电话号码或电子邮件地址。
   - 将联系信息存储在数据库中：
     - **设备令牌表：**供推送通知使用。
     - **用户表：**保存电子邮件地址和电话号码。

3. **通知发送流程：**

   <div style="margin-left:3rem">
      <img src="../../10.%20Notification%20System/images/high-level-design.png" alt="High Level Design" width="500">
   </div>

   - **触发服务：**
      - 生成用于启动通知的事件，例如账单提醒、物流更新。
      - 触发通知发送的服务可以是微服务、cron job 或分布式系统。
   - **通知服务器：**
      - 为其他服务提供发送通知的 API。
      - 执行基本校验，例如验证电子邮件地址和电话号码。
      - 查询数据库或缓存，获取渲染通知所需的数据。
   - **第三方服务：**向用户投递通知。

### 初始设计中的挑战
- **单点故障（SPOF）：**一台通知服务器崩溃可能导致整个系统不可用。
- **可扩展性问题：**难以独立扩展数据库、缓存和处理组件。
- **性能瓶颈：**发送通知需要大量资源。

### 改进设计

   <div style="margin-left:3rem">
      <img src="../../10.%20Notification%20System/images/improved-design.png" alt="Improved Design" width="500">
   </div>

- 将数据库和缓存从通知服务器中拆分出来。
- 通过多台通知服务器实现**横向扩展**。
- 使用**消息队列**解耦系统组件。
   - 需要发送大量通知时，消息队列可以作为缓冲区。
- 增加从消息队列拉取通知事件的 worker，并将通知发送到对应的第三方服务。

---

## 第 3 步：深入设计

### 可靠性
1. **防止数据丢失：**
   <div style="margin-left:3rem">
   <img src="../../10.%20Notification%20System/images/data-loss.png" alt="Data Loss" width="400">
   </div>

   - 将通知数据持久化到数据库，并实现重试机制。
   - 加入通知日志数据库以持久保存数据。

2. **去重：**
   - 检查事件 ID，避免重复发送通知。
   - 通知事件首次到达时，根据事件 ID 检查是否已处理过。如果处理过就丢弃，否则发送通知。

### 其他组件
   <div style="margin-left:3rem">
   <img src="../../10.%20Notification%20System/images/events-tracking.png" alt="Events Tracking" width="400">
   </div>

1. **通知模板：**预先格式化的模板可以让通知保持一致并提高效率。
2. **通知设置：**
   - 用户可以选择启用或关闭特定渠道（推送、短信或电子邮件）。
   - 将设置保存在专用的通知设置表中。
3. **限流：**限制向用户发送通知的频率。
4. **重试机制：**第三方服务故障时，重试发送通知。
5. **队列监控：**跟踪排队中的通知，以便动态扩缩 worker。
6. **事件跟踪：**收集打开率、点击率和互动率等指标。

### 安全
使用 **AppKey** 和 **AppSecret** 对推送通知 API 进行身份验证和保护。

### 通知流程

   <div style="margin-left:3rem">
   <img src="../../10.%20Notification%20System/images/updated-design.png" alt="Updated Design" width="500">
   </div>

1. 触发服务调用 API 发送通知。
2. 通知服务器校验请求，并从缓存或数据库中获取元数据。
3. 将通知事件发送到消息队列。
4. worker 处理事件，并与第三方服务交互。
5. 第三方服务将通知投递给用户。

---

## 关键优化
1. **横向扩展：**增加通知服务器来分担负载。
2. **消息队列：**解耦处理流程，以应对大量通知。
3. **缓存：**缓存频繁访问的数据，以降低延迟。
4. **分布式抓取：**在不同地理位置优化消息投递，以提高性能。
