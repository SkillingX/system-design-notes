# 第 6 章：设计键值存储

## 引言
**键值存储**是一种非关系型数据库，以键值对的形式存储数据。每个键都是唯一的，客户端通过键访问对应的值。本章介绍如何设计一个可扩展、高可用的分布式键值存储，并支持以下操作：
- `put(key, value)`：写入数据。
- `get(key)`：读取数据。

### 设计特点
- 键值对较小（小于 10 KB）。
- 支持大数据量，并具备高可用性和可扩展性。
- 支持自动扩展和可调节的一致性。
- 延迟低。

---

## 单服务器键值存储
### 实现方式
- 使用**哈希表**在内存中存储键值对。
- 优化方式：
  - 压缩数据。
  - 将不常访问的数据存储在磁盘上。

### 局限性
单台服务器的内存有限。要提高可扩展性，需要采用**分布式方案**。

---

## 分布式键值存储
**分布式键值存储**会将数据分区并分布到多台服务器上，同时需要处理 **CAP 定理**所描述的权衡。

### CAP 定理
1. **一致性（Consistency）：**所有客户端在同一时刻看到相同的数据。
2. **可用性（Availability）：**即使部分节点宕机，系统也会对每个请求作出响应。
3. **分区容错性（Partition Tolerance）：**出现网络分区时，系统仍能继续运行。

**权衡：**根据 CAP 定理，三项保证中只能同时实现两项。

<p align="center">
  <img src="../../06.%20Key-Value%20Store/images/cap.png" alt="CAP" width="400">
</p>

#### 系统类型
- **CP 系统：**保证一致性和分区容错性，牺牲可用性，例如银行系统。
- **AP 系统：**保证可用性和分区容错性，牺牲强一致性，例如最终一致性系统。
- **CA 系统：**保证一致性和可用性，牺牲分区容错性。

    **网络故障无法避免，因此分布式系统必须能够容忍网络分区。所以，CA 系统无法在真实世界的应用中成立。**

    分布式系统中不可避免会出现网络分区。一旦发生分区，就必须在一致性和可用性之间作出选择。例如，节点 n3 宕机后，写入 n1 或 n2 的数据无法传播到 n3。反过来，如果数据写入 n3，但还没传播到 n1 和 n2，n1 和 n2 上的数据就会过期。

    <p align="center">
    <img src="../../06.%20Key-Value%20Store/images/server-down.png" alt="Server down" width="400">
    </p>

- 如果选择 CP 系统，就必须阻止对 n1 和 n2 的所有写操作，以避免数据不一致。
- 如果选择 AP 系统，系统会继续接受读取请求，即使返回的数据可能已经过期。对于写操作，n1 和 n2 会继续接受写入；网络分区恢复后，数据会同步到 n3。

## 系统组件
### 1. 数据分区
- **技术：**使用一致性哈希将数据均匀分布到多台服务器。
- **优点：**
  - 增加或移除服务器时可以自动扩展。
  - 通过虚拟节点适配不同服务器的容量。服务器的虚拟节点数量与其容量成正比。

### 2. 数据复制
- 将数据复制到 `N` 台服务器上，以实现高可用。
- 沿哈希环从服务器所在位置开始顺时针遍历，选择最先遇到的 N 台服务器来存储数据副本。为提高可靠性，应将副本放在不同的数据中心中。

    <p align="center">
    <img src="../../06.%20Key-Value%20Store/images/data-replication.png" alt="Data replication" width="300">
    </p>

### 3. 一致性
数据会复制到多个节点，因此必须在各副本之间同步。
- **Quorum 共识：**
  - `N`：副本总数。
  - `W`：写入 quorum 数量。写操作要被视为成功，必须获得 W 个副本的确认。
  - `R`：读取 quorum 数量。读取操作要被视为成功，必须等待至少 R 个副本响应。
  - **规则：**`W + R > N` 可以保证强一致性。
  - W、R 和 N 的配置需要在延迟与一致性之间权衡。

    <p align="center">
    <img src="../../06.%20Key-Value%20Store/images/quorum-consensus.png" alt="Quorum consensus" width="400">
    </p>

    - 如果 `R = 1` 且 `W = N`，系统针对快速读取进行了优化。
    - 如果 `W = 1` 且 `R = N`，系统针对快速写入进行了优化。
    - 如果 `W + R > N`，可以保证强一致性（通常 `N = 3`，`W = R = 2`）。
    - 如果 `W + R <= N`，则无法保证强一致性。

- **一致性模型：**
  - **强一致性：**读取操作返回与最新一次成功写入对应的值。
  - **弱一致性：**后续读取可能看不到最新值。
  - **最终一致性：**经过足够长的时间后，所有更新都会传播到各个副本，副本最终保持一致。

### 4. 不一致性处理
数据复制可以提高可用性，但也会导致各副本之间出现不一致。可以使用版本和向量时钟解决不一致问题。
- **版本控制：**
    - 使用**向量时钟**跟踪数据版本并解决冲突。
    - 版本控制是指将每次数据修改都视为一个新的、不可变的数据版本。
        <div>
        <img src="../../06.%20Key-Value%20Store/images/consistent-server.png" alt="Consistent hashing" width="400">
        <img src="../../06.%20Key-Value%20Store/images/inconsistent-server.png" alt="Inconsistent server" height="230">
        </div>

    - 服务器 1 修改了姓名，服务器 2 也同时修改了姓名。这两次修改并发发生，因此产生了两个冲突值，分别称为版本 v1 和 v2。

- **向量时钟：**
    1. **设置：**向量时钟是与数据项关联的一组 `[server, version]` 对。它可以判断一个版本是另一个版本的前序、后继，还是与之冲突。
        - 假设向量时钟表示为 `D([S1, v1], [S2, v2], …, [Sn, vn])`。如果数据项 D 写入服务器 Si，系统需要执行以下操作之一。
        - 其中，`D` 是数据项，`Si` 是服务器标识符，`vi` 是服务器 `Si` 上该数据的版本计数器。

    2. **更新向量时钟：**数据项在服务器上修改时：
        - 如果该服务器已在向量时钟中，则递增它对应的版本计数器。
        - 否则，在向量时钟中新增一项。

    3. **冲突检测：**
        - **无冲突：**如果版本 X 中的所有计数器都小于或等于版本 Y 中对应的计数器，则 X 是 Y 的祖先版本。
        - **存在冲突：**如果两个版本互为兄弟版本，则至少有一个计数器与另一个版本中的对应计数器不满足前序关系。

    4. **冲突解决：**检测到冲突（兄弟版本）后，由应用特定逻辑或客户端介入来协调数据。

        <p align="center">
        <img src="../../06.%20Key-Value%20Store/images/vector-clock.png" alt="Vector clock" width="500">
        </p>

- **挑战：**
  - 增加了客户端的复杂度。
  - 更新较多时，向量时钟可能不断变大，因此需要截断策略来限制其大小。

### 5. 故障处理

#### a. 故障检测
不能仅仅因为一台服务器报告某个服务器宕机，就认定它确实宕机。通常至少需要两个独立的信息来源才能将服务器标记为宕机。
- **Gossip 协议：**
    <div style="margin-left:3rem">
        <img src="../../06.%20Key-Value%20Store/images/gossip-protocol.png" alt="Gossip protocol" width="600">
    </div>

    - 每个节点维护成员 ID 和心跳计数器。
    - 每个节点定期递增自己的心跳计数器。
    - 每个节点定期向一组随机节点发送心跳。
    - 如果成员的心跳计数器在超过预设时间后仍未递增，就将其视为离线。

#### b. 临时故障
- **Sloppy Quorum：**暂时使用健康节点来维持系统运行。
        <p align="center">
        <img src="../../06.%20Key-Value%20Store/images/sloppy-quorum.png" alt="Sloppy Quorum" width="400">
        </p>

    - 检测到故障后，系统需要采取措施来保证可用性。
    - 系统不再严格执行 quorum 要求，而是在哈希环上选择最先遇到的 W 台健康服务器处理写入，并选择最先遇到的 R 台健康服务器处理读取。
    - 忽略离线服务器。如果某台服务器不可用，其他服务器会暂时处理请求。

- **Hinted Handoff：**离线服务器恢复后补上期间错过的变更。
    - 故障服务器恢复后，将变更推送回该服务器，以实现数据一致。

#### c. 永久故障
- 使用 **Merkle Tree** 高效地同步副本。
  **Merkle Tree**（也称哈希树）是一种数据结构，可在永久故障期间高效检测并解决副本之间的不一致。

- 工作方式：
    1. **结构：**
        - **叶节点**保存单个数据块的哈希值。
        - **非叶节点**保存其子节点的哈希值。
        - **根哈希**代表整棵树中的数据状态。

    2. **构建 Merkle Tree：**
        - **步骤 1：**将键空间划分为多个 bucket。

            <img src="../../06.%20Key-Value%20Store/images/key-bucket.png" alt="Key Bucket" width="500">

        - **步骤 2：**使用均匀哈希对每个 bucket 中的键进行哈希。

            <img src="../../06.%20Key-Value%20Store/images/hash-key-bucket.png" alt="Hash Key Bucket" width="500">

        - **步骤 3：**为每个 bucket 生成一个哈希值。

            <img src="../../06.%20Key-Value%20Store/images/hash-bucket.png" alt="Hash Bucket" width="500">

        - **步骤 4：**合并各 bucket 的哈希值，计算更高层的哈希，最终得到根哈希。

            <img src="../../06.%20Key-Value%20Store/images/merkel-tree.png" alt="Merkle Tree" width="500">

    3. **同步：**
        - 同步两个副本时：
            - 比较两个副本的根哈希。
            - 根哈希相同，则副本一致。
            - 根哈希不同，则递归比较子节点哈希，以找出不一致的 bucket。
        - 只同步存在差异的数据。

- 优点：
    - **高效：**只同步不一致的数据，减少数据传输。
    - **可扩展：**适用于大型数据集，同步开销小。
    - **可靠：**确保副本之间的数据一致。

### 6. 处理数据中心故障
- 在多个数据中心之间复制数据，以确保其中一个数据中心故障时仍然可用。

## 写入与读取路径

- 缓存写满后，将数据刷新到磁盘上的 **SSTable**（Sorted String Table，有序字符串表）。

## 最终架构

<p align="center">
<img src="../../06.%20Key-Value%20Store/images/final-architecture.png" alt="Final architecture" width="500">
</p>

- 客户端通过简单的 API `get(key)` 和 `put(key, value)` 与键值存储交互。
- 协调器是一个节点，充当客户端与键值存储之间的代理。
- 各节点使用一致性哈希分布在环上。
- 系统完全去中心化，因此可以自动添加和移动节点。
- 数据复制在多个节点上。
- 所有节点承担相同的一组职责，因此不存在单点故障。
