# 第 26 章：支付系统

## 简介

本章将设计一个**支付系统**。现代**电子商务**都离不开支付系统。

**支付系统**用于完成金融交易，转移货币价值。

---

## 第一步：理解问题并明确设计范围

- C：我们要构建什么类型的支付系统？
- I：为电子商务系统构建支付后端，类似 Amazon.com，处理所有与资金流转有关的事情。
- C：支持哪些支付方式？信用卡、PayPal、银行卡等？
- I：实际系统需要支持所有这些方式。面试题中可以只考虑信用卡支付。
- C：我们自己处理信用卡支付吗？
- I：不，我们使用 Stripe、Braintree、Square 等第三方服务提供商。
- C：系统会存储信用卡数据吗？
- I：出于合规原因，我们不会在自己的系统中直接存储信用卡数据，而是依赖第三方支付处理商。
- C：应用是全球化的吗？需要支持不同币种和国际支付吗？
- I：应用面向全球，但面试中假设只使用一种货币。
- C：每天需要支持多少笔支付交易？
- I：每天 100 万笔交易。
- C：是否需要支持付款流程，例如每月向收款方打款？
- I：需要支持。
- C：还有什么需要注意的？
- I：需要支持对账，以修复与内部和外部系统通信时出现的不一致。

### **功能性需求**

- **收款（Pay-in）流程**：支付系统代表商家向顾客收款。
- **付款（Pay-out）流程**：支付系统向世界各地的卖家付款。

### **非功能性需求**

- 可靠性和容错能力。需要谨慎处理支付失败。
- 建立内部系统与外部系统之间的对账机制。

### **粗略估算**

系统每天需要处理 100 万笔交易，即每秒约 10 笔。

对于任何数据库系统来说，这都不算高吞吐量，因此本次面试不聚焦于吞吐量。

### **收款流程**

收款流程的高层概览如下：

<div style="margin-left:3rem">
    <img src="../../26.%20Payment%20System/images/payin-flow-high-level.png" alt="收款流程高层设计" width="500" />
</div>

- **支付服务**：接收支付事件并协调支付流程。通常还会使用第三方服务检查洗钱违规或犯罪活动等风险。
- **支付执行器**：通过支付服务提供商（PSP）执行单笔支付订单。一项支付事件可能包含多个支付订单。
- **支付服务提供商（PSP）**：将资金从一个账户转移到另一个账户，例如从买家的信用卡账户转到电子商务网站的银行账户。
- **卡组织**：负责处理信用卡业务的组织，例如 Visa、Mastercard 等。
- **账本（Ledger）**：记录所有支付交易的财务账目。
- **钱包**：记录所有商家的账户余额。

收款流程示例：

- 用户点击“下单”，支付事件被发送到支付服务。
- 支付服务将事件存入数据库。
- 支付服务调用支付执行器，处理该支付事件中的所有支付订单。
- 支付执行器将支付订单存入自己的数据库。
- 支付执行器调用外部 PSP 处理信用卡付款。
- 支付执行器完成付款后，支付服务更新钱包，记录卖家的收款金额。
- 钱包服务将更新后的余额存入数据库。
- 支付服务调用账本，记录所有资金变动。

### **支付服务 API**

~~~http
POST /v1/payments
{
  "buyer_info": {...},
  "checkout_id": "some_id",
  "credit_card_info": {...},
  "payment_orders": [{...}, {...}, {...}]
}
~~~

`payment_order` 示例：

~~~json
{
  "seller_account": "SELLER_IBAN",
  "amount": "3.15",
  "currency": "USD",
  "payment_order_id": "globally_unique_payment_id"
}
~~~

需要注意：

- `payment_order_id` 会传递给 PSP，用于去重支付，也就是作为幂等键。
- `amount` 字段的类型是 `string`，因为 `double` 不适合表示货币金额。

~~~http
GET /v1/payments/{:id}
~~~

该端点根据 `payment_order_id` 返回单笔支付的执行状态。

### **支付服务数据模型**

需要维护两张表：`payment_events` 和 `payment_orders`。

对于支付系统，性能通常不是最重要的因素，但强一致性很重要。

选择数据库时还需考虑：

- DBA 人才市场充足，便于招聘人员管理数据库。
- 数据库已在其他大型金融机构中得到验证。
- 配套工具丰富。
- 选择传统 SQL 数据库而非 NoSQL/NewSQL，以获得 ACID 保证。

`payment_events` 表包含：

- `checkout_id`：字符串，主键。
- `buyer_info`：字符串（作者注：可能更适合使用其他表的外键）。
- `seller_info`：字符串（作者注：同上）。
- `credit_card_info`：内容取决于卡组织。
- `is_payment_done`：布尔值。

`payment_orders` 表包含：

- `payment_order_id`：字符串，主键。
- `buyer_account`：字符串。
- `amount`：字符串。
- `currency`：字符串。
- `checkout_id`：字符串，外键。
- `payment_order_status`：枚举值（`NOT_STARTED`、`EXECUTING`、`SUCCESS`、`FAILED`）。
- `ledger_updated`：布尔值。
- `wallet_updated`：布尔值。

需要注意：

- 一项支付事件可以关联多笔支付订单。
- 收款流程不需要 `seller_info`，只有付款流程需要。
- 调用相应服务记录支付结果后，会更新 `ledger_updated` 和 `wallet_updated`。
- 后台任务会检查正在处理的支付状态；如果支付在合理时间内仍未处理完成，就触发告警。

### **复式记账系统**

复式记账机制是任何支付系统的核心。它通过同时对两个账户应用资金操作来跟踪资金流动：一个账户余额增加（贷记），另一个账户余额减少（借记）。

| 账户 | 借记 | 贷记 |
|------|------|------|
| 买家 | $1 | |
| 卖家 | | $1 |

所有交易条目的总和始终为零。这种机制能够端到端追踪系统中的所有资金流动。

付款流程的组件与收款流程非常相似。

主要区别：

## 第三步：深入设计

本节重点讨论如何提高系统速度、健壮性和安全性。

### **PSP 集成**

如果系统可以直接连接银行或卡组织，就可以不通过 PSP 进行支付。这种连接非常少见，通常只有能够证明投资合理性的大型公司才会选择。

如果采用传统方式，可以通过以下两种方式之一集成 PSP：

- 通过 API 集成，前提是支付系统能够收集支付信息。
- 使用托管支付页面，以避免处理支付信息相关的监管要求。

托管支付页面的工作流程如下：

<div style="margin-left:3rem">
    <img src="../../26.%20Payment%20System/images/hosted-payment-page-workflow.png" alt="托管支付页面工作流" width="500" />
</div>

- 用户在浏览器中点击“结账”按钮。
- 客户端将支付订单信息发送给支付服务。
- 支付服务收到支付订单信息后，向 PSP 发送支付登记请求。
- PSP 收到货币、金额、过期时间等支付信息，以及用于幂等处理的 UUID（通常是支付订单的 UUID）。
- PSP 返回一个唯一标识该支付登记的令牌。支付服务将令牌存入数据库。
- 令牌存储后，系统向用户展示 PSP 托管的支付页面。页面使用该令牌和成功/失败后的跳转 URL 进行初始化。
- 用户在 PSP 页面填写支付信息，PSP 处理付款并返回支付状态。
- 用户随后被重定向到 redirectURL。例如：`https://your-company.com/?tokenID=JIOUIQ123NSF&payResult=X324FSa`。
- 与此同时，PSP 会通过 webhook 异步调用支付服务，通知后端支付结果。
- 支付服务根据收到的 webhook 记录支付结果。

### **对账**

前一节介绍了支付成功时的正常流程。异常流程则通过后台对账过程发现并处理。

PSP 每晚会发送结算文件，系统使用该文件比较外部系统与内部系统的状态：

<div style="margin-left:3rem">
    <img src="../../26.%20Payment%20System/images/settlement-report.png" alt="结算报告" width="500" />
</div>

该过程也可用于检测内部不一致，例如账本服务和钱包服务之间的数据差异。

财务团队会手动处理差异，可分为：

- **可分类且可自动调整**：已知类型的差异，可以通过标准流程调整。
- **可分类但无法自动处理**：由财务团队手动调整。
- **无法分类**：由财务团队手动调查并调整。

### **处理支付延迟**

有些支付需要数小时才能完成，尽管通常只需几秒钟。

可能原因包括：

- 支付被标记为高风险，需要人工审核。
- 信用卡需要额外保护，例如 3D Secure 身份验证，需要持卡人提供更多信息才能完成支付。

处理方式：

- 等待 PSP 在支付完成时发送 webhook；如果 PSP 不提供 webhook，则轮询其 API。
- 向用户显示“处理中”状态，并提供页面供用户查询支付进度。支付完成后，也可以发送邮件通知用户。

### **内部服务之间的通信**

服务之间通常有两种通信模式：同步和异步。

同步通信（即 HTTP）适用于小规模系统，但规模扩大后会出现问题：

- **性能低**：随着调用链中的服务增加，请求/响应周期变长。
- **故障隔离能力差**：如果 PSP 或其他服务故障，用户可能无法收到响应。
- **耦合紧密**：发送方需要知道接收方。
- **难以扩展**：没有缓冲区，难以应对流量突然增长。

异步通信可以分为两类。

单接收者模式：多个接收者订阅同一主题，但每条消息只处理一次：

<div style="margin-left:3rem">
    <img src="../../26.%20Payment%20System/images/single-receiver.png" alt="单接收者模式" width="500" />
</div>

多接收者模式：多个接收者订阅同一主题，每条消息都会转发给所有接收者：

<div style="margin-left:3rem">
    <img src="../../26.%20Payment%20System/images/multiple-receiver.png" alt="多接收者模式" width="500" />
</div>

后一种模式适用于支付系统，因为一次支付可能触发多个副作用，分别由不同服务处理。

简而言之，同步通信比较简单，但无法让服务自主运行；异步通信则以简单性和一致性为代价，换取可扩展性和韧性。

### **处理支付失败**

任何支付系统都需要处理支付失败。可以通过以下机制实现：

- **跟踪支付状态**：支付失败时，根据支付状态决定是否重试或退款。
- **重试队列**：将需要重试的支付发布到重试队列。
- **死信队列**：将最终失败的支付放入死信队列，以便调试和检查。

### **恰好一次投递**

需要确保每笔支付只处理一次，避免重复向顾客扣款。

如果一个操作同时满足“至少执行一次”和“最多执行一次”，那么它就恰好执行一次。

为了保证至少执行一次，需要使用重试机制：

<div style="margin-left:3rem">
    <img src="../../26.%20Payment%20System/images/retry-mechanism.png" alt="重试机制" width="500" />
</div>

常见的重试间隔策略：

- **立即重试**：请求失败后，客户端立即再次发送请求。
- **固定间隔**：等待固定时长后再重试支付。
- **递增间隔**：每次重试都逐步延长等待时间。
- **指数退避**：每次重试都将等待时间加倍。
- **取消**：客户端取消请求，通常是因为错误不可恢复或已达到重试上限。

一般来说，默认采用指数退避策略是合适的。服务器最好通过 `Retry-After` 响应头指定重试间隔。

重试可能导致服务器重复处理支付：

- 用户重复点击“支付”按钮，从而被扣款两次。
- PSP 已成功处理支付，但下游服务（账本、钱包）未能处理；重试又导致 PSP 再次处理该笔支付。

要解决重复支付问题，需要使用幂等机制：同一个操作无论应用多少次，都只处理一次。

从 API 角度看，客户端可以多次调用并得到相同结果。幂等性通过请求中的特殊头部（例如 `idempotency-key`）实现，该值通常是 UUID。

<div style="margin-left:3rem">
    <img src="../../26.%20Payment%20System/images/idempotency-example.png" alt="幂等示例" width="500" />
</div>

可以利用数据库的唯一键约束实现幂等：

- 服务器尝试在数据库中插入新行。
- 插入操作因违反唯一键约束而失败。
- 服务器识别该错误，并将现有对象返回给客户端。

PSP 端也会应用幂等机制，使用前文提到的 nonce。PSP 会确保不会使用同一个 nonce 重复处理支付。

### **一致性**

支付生命周期中会涉及多个有状态服务：PSP、账本、钱包和支付服务。

任意两个服务之间的通信都可能失败。通过实现恰好一次处理和对账，可以确保所有服务最终达到数据一致。

如果使用复制，还需要处理复制延迟，这可能导致用户从主数据库和副本数据库读到不一致的数据。

为了缓解这一问题，可以让所有读写都由主数据库处理，只使用副本提供冗余和故障转移。另一种方案是使用 Paxos 或 Raft 等共识算法确保副本始终同步。也可以使用基于共识的分布式数据库，例如 YugabyteDB 或 CockroachDB。

### **支付安全**

可以使用以下机制保障支付安全：

- **请求/响应窃听**：使用 HTTPS 保护所有通信。
- **数据篡改**：强制加密并监控完整性。
- **中间人攻击**：使用 SSL 和证书固定。
- **数据丢失**：跨多个区域复制数据，并创建数据快照。
- **DDoS 攻击**：实施限流和防火墙策略。
- **信用卡被盗**：使用令牌，避免在系统中保存真实卡片信息。
- **PCI 合规性**：处理品牌信用卡的组织需要遵守的一项安全标准。
- **欺诈**：使用地址验证、卡片验证码（CVV）、用户行为分析等方式防范。

## 第四步：总结

还可以讨论：

- 监控和告警。
- 调试工具：需要方便地了解支付失败原因的工具。
- 货币兑换：国际化支付系统需要考虑这一点。
- 地理区域：不同地区可能使用不同的支付方式。
- 现金支付：在印度、巴西等地非常普遍。
