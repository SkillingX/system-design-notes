# 第 2 章：数量级估算

## 引言
数量级估算是系统设计面试中的一项重要技能。它通过快速、粗略的计算，评估系统容量或性能。Google Senior Fellow Jeff Dean 指出，这类估算可以通过思想实验和常见性能基准，帮助判断设计是否满足需求。

本章介绍可扩展性估算所需的关键概念、方法和示例。

### 每位程序员都应该了解的延迟数据
延迟数据表示计算系统执行各种操作所需的时间，可以帮助我们了解不同操作之间的相对性能：

| 操作 | 延迟（2020 年） |
|--------------------------|----------------|
| L1 缓存访问 | 0.5 ns |
| L2 缓存访问 | 7 ns |
| 主内存访问 | 100 ns |
| SSD 随机读取 | 150 µs |
| HDD 随机寻道 | 10 ms |
| 数据中心内往返 | 500 µs |
| 跨区域数据中心往返 | 150 ms |

**要点：**
- 内存很快，磁盘较慢。
- 尽可能避免磁盘寻道。
- 通过互联网传输数据前先压缩，以节省带宽。

---

### 可用性数据
高可用性（HA）可以尽量减少停机时间。可用性通常用“几个 9”来表示：
- <strong>99%（两个 9）：</strong>每年约停机 3.65 天
- <strong>99.9%（三个 9）：</strong>每年约停机 8.8 小时
- <strong>99.99%（四个 9）：</strong>每年约停机 52 分钟
- <strong>99.999%（五个 9）：</strong>每年约停机 5.3 分钟
- <strong>99.9999%（六个 9）：</strong>每年约停机 31.56 秒

Amazon、Google 和 Microsoft 等云服务商的服务等级协议（SLA）通常以 **99.9% 或更高**的可用性为目标。

## 第 2 节：估算示例——Twitter 的 QPS 与存储需求

### 假设
- **月活跃用户（MAU）：3 亿。**
- **日活跃用户（DAU）：月活跃用户的 50%。**
- **每位用户平均每天发布推文数：2 条。**
- **包含媒体内容的推文比例：10%。**
- **数据保留时间：5 年。**

### 估算
1. **每秒查询数（QPS）：**
   - DAU = \( 300M x 50\% = 150M \)
   - 推文 QPS = \( 150M x 2 tweets / 24 hour / 3600 seconds = ~3500 )
   - 峰值 QPS = \( 2 x 3500 = ~7000 \)

2. **媒体存储：**
   - **推文大小组成：**
     - `tweet_id`：64 字节
     - `text`：140 字节
     - `media`：1 MB
   - **每日媒体存储量：**\( 150M x 2 x 10\% x 1MB = 30TB per day \)
   - **5 年存储量：**\( 30TB x 365 x 5 = ~55PB \)

## 第 3 节：有效估算技巧

### 1. 取整与近似
不必过度追求精确，重点是计算过程。可以用整数量级简化复杂计算。例如：
- \( 99987 / 9.1 \) 可以近似为 \( 100,000 / 10 = 10,000 \)。

### 2. 记录假设
清楚写下假设，便于后续查阅。

### 3. 标注单位
标注单位以避免歧义，例如写 `5 MB`，而不是只写 `5`。

### 4. 常见估算场景
- <strong>QPS（每秒查询数）：</strong>衡量流量强度。
- <strong>峰值 QPS：</strong>考虑流量高峰。
- <strong>存储需求：</strong>估算所需的总数据容量。
- <strong>缓存需求：</strong>评估缓存所需的内存。
- <strong>服务器数量：</strong>根据工作负载估算硬件需求。
